Reusing instrumentation headers

A tool-owned Clang PCH lets a new translation unit reuse headers parsed for an earlier file. The investigation tested existing package sources under GCC, Clang, and MSVC in Windows Docker.

Decision: not adopted

    What limits the gain

    Preparation needs reuse

    The broad policy covered 70 GTest-linked targets. Many have one source and pay preparation without another file to amortize it. The targeted policy covered 15 multi-source targets.

    Parsing work moves into the fold

    For a representative GCC source, AST parsing dropped from 2.018s to 0.519s while matching rose from 0.287s to 0.587s. Deserializing cached declarations still costs time.

    First-file memory rises

    GCC peak RSS rose from 223 to 292 MiB on the first core file. The next file fell from 222 to 210 MiB. JSON showed the same tradeoff: more memory during preparation, less on later files.

    GCC’s application PCH has an ordering issue

    The existing integration puts generated reflection before the user PCH on instrumented targets. GCC then parses the wrapper normally. Moving reflection after the PCH made GCC actually consume it, confirmed with -H; the general fix remains separate.

    Method and limits

    • The master-based clean builds have one run per configuration. The disabled-path probe and earlier small existing-source comparisons used three alternating rounds. Build-only results and earlier configure/build/CTest totals are separate experiments.
    • Instrumentation times come from all reported tool phases. Native compile times come from the first invocation in each .ninja_log, matched through compile_commands.json. Later CTest-triggered rebuilds are excluded from the per-file distribution.
    • Per-file distributions match every selected configuration against master by source and target/standard variant. Only matching repository C++ sources are included; fetched dependencies, links, and standalone PCH-generation commands are excluded from the per-file table. PCH-generation and link costs remain in the clean-build wall times.
    • Cold-prefix costs are charged to the source that incurred them. Scheduler order can change which file prepares a prefix. Per-file stage durations include contention and waiting; they are not CPU times.
    • GCC 15.2 and Clang 21.1 were checked in Linux Docker; MSVC 19.44 was checked using docker.exe --context windows. Every package uses embedded LLVM 22.1.8. The master-based package comparison is GCC only. The earlier Clang and MSVC checks compare prototype cache settings.
    • Direct/transitive header changes, touch-only invalidation, truncated manifests, parallel generation, and unchanged rebuilds were checked. The experimental cache still needs hardening before production use.
